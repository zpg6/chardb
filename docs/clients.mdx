CharDB includes a React client for browser applications and a native Rust client for services and command-line programs in this repository. Registry publication is still pending. Both use registered query and mutation handles rather than accepting SQL from the caller.

## React

The React client lives in `packages/react` and is wired into the generated workspace. The npm package is not public yet.

Configure the client with the same public URL that serves Better Auth and the CharDB Worker:

```tsx src/web/App.tsx
import { anonymousClient, jwtClient, organizationClient } from "better-auth/client/plugins";
import { createAuthClient } from "better-auth/react";
import { createChardbReactClient } from "@chardb/react";

export const db = createChardbReactClient({
  url: window.location.origin,
  ownership: "organization",
  auth: ({ baseURL }) => createAuthClient({
    baseURL,
    plugins: [anonymousClient(), organizationClient(), jwtClient()],
  }),
});
```

`createChardbReactClient` uses that URL for Better Auth, live WebSockets, and organization file routes. It preserves Better Auth's inferred client plugins and adds the verified user or active organization to query and mutation arguments.

Follow [Live queries](/live-queries) for the client setup and [Files](/files) for the organization-scoped file API.

## Rust

The `chardb-client` crate lives in `rust/chardb` and provides blocking and runtime-neutral async APIs over protocol version 3. The crate is not public on crates.io yet.

Typed `Query<Arguments, Row>` and `Mutation<Arguments, Output>` handles bind each server reference to its Serde request and response types. The default build includes both client styles and Rustls; optional features select native roots or JSON Schema introspection.

Declare where each module goes on the app, then run `bunx @chardb/core generate` in the app directory:

```ts src/worker.ts
export const app = chardb({
  ownership: "organization",
  auth,
  schema,
  api,
  clients: { rust: "src/chardb_api.rs", ts: "src/chardb_api.ts" },
});
```

The Rust module holds those handles and their Serde types from the registered queries and tables: one `Serialize` struct per `args` validator (any Standard JSON Schema validator, such as zod 4), one `Deserialize` row struct per selected table, and a `Query` or `Mutation` const per handle. Mutation results and handles without an `args` validator use `serde_json::Value`. Row types come from one sample compile per query, so a query whose table depends on its arguments gets the first branch's row. `migrations generate` refreshes every declared module once the migration is written and fails with its own message if it cannot. The modules are compared byte for byte, so exclude them from formatters, and add `--check` in CI to fail when a committed module is stale.

The `ts` module exports the same handles as `QueryHandle` and `MutationHandle` constants with their argument and row types, for TypeScript consumers outside the Vite build that pass them to `createChardbClient`.

While `vite dev` runs and the app declares `clients`, the `chardb()` Vite plugin runs `chardb generate` at startup and after each source change (Bun must be on `PATH`); `chardb({ generate: false })` turns that off.

The Rust client supports registered live queries, mutations, reconnects, mutation replay, and auth refresh. Your application must obtain the initial Better Auth JWT and provide refreshed JWTs when the client requests one. The crate does not perform sign-in. It also does not implement files, vectors, `workers-rs`, or `wasm32` transport.

The crate README at `rust/chardb/README.md` covers connection, TLS, timeout, and feature details.
