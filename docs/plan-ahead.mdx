---
title: "Plan ahead"
description: "Know CharDB's recovery, scale, and availability limits."
---

CharDB is experimental. It has no production availability SLA, automatic regional failover, or load-based resharding. Decide how you will recover data and when you will move a shard before either becomes urgent.

## Take recovery points

Deployed SQLite-backed Durable Objects retain native point-in-time recovery history for 30 days. CharDB can capture one recovery point across the Catalog and every active Cdb shard:

Run the command with the same `CHARDB_ADMIN_TOKEN` configured for the deployed Worker.

```sh
bunx @chardb/core backups create --url https://api.example.com --out recovery.json
```

Store the manifest outside the deployment. To restore it:

```sh
bunx @chardb/core backups restore --url https://api.example.com --from recovery.json
```

Restore validates the manifest and topology, fences Catalog and every shard, clears CharDB's live R2 keys and tracked Vectorize records, and restarts the Durable Objects at their recorded bookmarks. The CLI drives large restores through signed, bounded turns, then rebuilds every authoritative file and vector head before returning. Rerun the same command after an unknown result. The manifest digest prevents a different recovery point from crossing an active fence. Test the procedure against a disposable deployed Worker. Native PITR is not available in Miniflare.

File uploads write an authoritative content-addressed object in the bound R2 bucket. CharDB does not set an expiry rule on that private prefix. Ordinary reads verify and stream those bytes without creating a live key. Restore verifies them again while rebuilding the canonical live keys. A failed provider cleanup leaves the recovery fence in place so the same command can resume. Rejected uploads and deleted files can leave invisible, billable content until provider-wide orphan collection is available.

## Record the deployed shape

Keep the Worker version, migration journal, schema version and digest, Durable Object namespace bindings, recovery-point manifest, and any active migration or range-movement ID together.

Monitor CharDB error codes and business-level row counts for data whose absence matters. If a migration, restore, or range movement has an unknown outcome, keep traffic closed until its durable state is known.

## Leave shard headroom

An organization or user is the placement and transaction boundary. Each shard reports its SQLite size to the Resharder once it passes 5 GiB, half of the Durable Object cap. The Resharder scans that shard's registered tables in pages, takes the prefix of its heaviest range that holds nearest half of those rows, and moves it, with its file metadata, vector state, outboxes, and tombstones, into the next `ShardDO_<n>`. It waits while a recovery point, a schema migration, or another movement is active. While an automatic move runs, those wait for it in turn, and writes on the source can see `CDB_RATE_LIMITED` if they outrun the capture log.

A shard is judged again only after its file grows a further quarter of the mark. A move that fails, or a shard whose rows sit in too few vshards to split, is logged and waits the same way. Name every shard `ShardDO_<n>`; any other name turns automatic splits off. To stop a running move, abort it by its logged id with `chardb experimental shards abort`.

Splits follow file size, not traffic. Set owner-level size and traffic limits in the application and watch latency and rate-limit errors. Workloads that require load-based balancing, cross-partition transactions, operator-controlled regional failover, or a production availability SLA are outside the current release.
